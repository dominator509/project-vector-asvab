content: the corpus the pack ships, and the way back from a rollback (REQ-003, REQ-022, REQ-023, REQ-048, REQ-056)

Round 28 made practice follow the objective the plan names. On the installation that mechanism was
a no-op for the three computable subtests -- the plan could name no objective for them, and a fresh
install held no items for them at all. This round ships them, and closes the two PENDING release
clauses while doing it.

The computable subtests are in the corpus, not generated on demand.
`examples/generate_corpus.rs` runs the application's own verify-store-activate pipeline with fixed
per-subtest seeds, and `rebuild-corpus.py` calls it for AR/MK/MC after the ingested subtests, so
the documented rebuild reproduces the corpus the pack is built from. `core-asvab v6` carries 6,961
items and declares 28 objectives over 9 subtests, so a plan names an objective for every subtest it
schedules and a fresh installation serves one without pressing "Prepare 40 questions".

A defect the readback caught. `check-corpus.py` reported 126 questions asked twice within one
subtest: the generated path refused only a repeated content hash, so the same question with its
wrong answers shuffled was stored again -- exactly the padding the ingestion loops already refuse
(one Electronics Information module asked its definitions up to seven times each; 3,668 items
carried 414 distinct questions). `generate_and_activate` now applies the question identity too,
and the rebuild stores 1,334 distinct questions instead of 1,500 rows with 166 repeats. The probe
also gained an independent re-derivation of every executable proof: 1,334 of 1,334 recompute to
the option they mark correct, evaluated in Python rather than trusted from the verifier.

Every claimed pack transition, against the installation's own store (DOD-035). install v6 over v5
(6,961 servable), rollback to v5 (the 1,334 generated items stay stored and leave service in one
statement), activate v6 again -- with the database hash recorded at each step. The transition back
did not work, and that is the finding: reinstalling the same signed pack reported success and
changed nothing, because `install` deliberately never undoes a rollback. That is the right safety
property, but on its own it makes a rollback a one-way door with no supported way home. The
documented `pack-activate` is that way now; it supersedes rather than quarantines the version it
replaces, so the transition repeats in either direction, and a test pins both halves.

A licence policy had to admit the computable subtests' own citation. `pack-install` refused v6
whole: the construct record's licence ("Facts-only; item text is original work") was outside the
permitted list. Named in it with the reasoning attached -- the page the citation names asserts all
rights reserved, so relabelling it public domain would be the dishonest fix; what keeps such a pack
honest is the executable proof the installer recomputes and the vault record whose bytes were
hashed when they were retrieved.

Clean room (DOD-002, DOD-023). A fresh clone of this commit ran the README's five published
commands in order -- install, preflight, generated-pack validation, the full 19-gate sweep,
evidence-archive verification -- and all five exited 0, with the lockfile digests and tool versions
recorded. The clone's artifact differs in bytes from the working copy's for the same source, which
is why no gate asserts digest equality across builds.

Zero state and the golden path (DOD-034). On a directory that did not exist, the exact release
artifact created and migrated its database, passed its own 19 checks, took the signed v6 pack
through the documented command, and completed the golden path: learner, 9-drill plan, one session
per named objective, attempts stored once (idempotence proven by submitting twice), analytics and
objective mastery read back, provenance re-checked. `examples/golden_path.rs` is new, and the soak
found a defect in it within minutes: its attempt ids named the item and session but not the
learner, so a repeated run looked like a duplicate submission. The machine is the developer's, so
the clause is PARTIAL with the virgin-OS residual named rather than claimed.

Abbreviated soak (DOD-038). `scripts/probes/soak.py` runs the packaged self-check plus a full
golden path per iteration against a copy of the installation's store, with a heartbeat, an
integrity check and a row census: 112 iterations over 12.02 minutes, 896 attempts added, 0
failures. The clause says an abbreviated trial is labelled separately and can never be PASS for the
full requirement, so the report says so and `release-state.py` reads that record rather than
asserting a duration. Both the soak and the zero-state lane were re-run after the final formatting
pass changed the artifact, because old evidence does not prove changed bytes.
